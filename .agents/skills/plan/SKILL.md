# 計画スキル

**トリガー:** `/plan` (またはユーザーが明示的に計画を求めた場合)

**説明:**
**適用範囲:** 計画のみの依頼では、計画成果物だけを作成し、ソースコードは編集しない。「まだ実装しない」という指定を守る。
計画と実装の両方が明示的に依頼されている場合、または後続の依頼で実装が指示された場合は、計画を整理してから依頼された実装へ進む。再依頼を一律に要求しない。

---

## 1. コンテキスト分析と調査
- **目的:** ユーザーのリクエストと既存のコードベース構造を理解する。
- **アクション:**
  - 関連ファイルを読み、現在の実装を理解します。
  - 依存関係、潜在的なリスク、アーキテクチャへの影響を特定します。
  - このステップ中にソースコードファイルを変更しないでください。

## 2. 成果物生成（"Brain" プロトコル）
- **目的:** 計画をエージェントのメモリ構造に永続化する。
- **厳格な要件:** 適切な計画ディレクトリ内のマークダウンファイルを作成または更新しなければなりません。
- **ディレクトリの安全性:**
  - ユーザー指定の保存先を優先し、指定がなければ `system-design/dev-plans/` を使う。存在しなければ作成する。既存ファイルの更新依頼は再確認せず、別用途のファイルとの衝突時は別名を選ぶか必要な確認を行う。
- **ファイル命名規則:**
  - デフォルト: `implementation_plan.md`
  - リファクタリング用: `refactoring_plan.md`
  - タスク用: `task.md`

## 3. 計画内容の要件
（`./.agents/rules/language-strategies.md` で定義された戦略に従ってください）
生成されるマークダウンファイルには、以下のセクションを含める必要があります:
1.  **目的:** 達成すべき内容の明確な要約。
2.  **分析（現状分析）:** 現状 vs 理想の状態。
3.  **提案される変更:**
    - 作成または変更するファイルのリスト。
    - 具体的なロジックの変更（擬似コードまたはシグネチャ）。
    - **検証計画:** 変更が機能することをどのように検証しますか？（例: 具体的なテストケース）。
4.  **リスク評価:** 回避すべき潜在的な副作用やハルシネーション。

## 4. 計画から実装への移行
- 計画のみの依頼では、計画を保存して結果を報告する。
- 実装も明示的に依頼されている場合は、その範囲で続行する。
- 「まだ変更しない」等の指定が解除されていない場合は実装しない。

---

**完了条件:** 計画のみか実装までかを現在の依頼に合わせる。依頼されていない実装を追加しない。
