# コミット・デプロイ承認・報告スキル (request-commit-deploy)

**トリガー:**
- コードやドキュメントの修正作業が完了し、コミットやデプロイの承認をユーザーに求めるとき。
- ユーザーから「コミットして」「デプロイして」と指示されて作業を行い、実行前の確認または実行完了の判断材料を提示するとき。

**目的:**
ユーザーがコミットやデプロイを実行・承認するにあたり、必要な判断材料（変更意図・方針・具体的な変更内容・検証結果）を過不足なく、かつ素早く把握できるようにする。

---

## 1. 報告の大原則

1. **簡潔な箇条書きの徹底:**
   - 長文の散文や過度な挨拶・前置きは書かない。
   - 各項目は箇条書き（`-`）で要点を絞って端的にまとめる。

2. **変更の意図（Why）を必ず明記する:**
   - 単なる「コードの差分（What）」の羅列は不可。
   - 「なぜその変更が必要だったのか（課題・要望）」および「なぜその方針・設計を選んだのか（設計上の理由・アプローチの妥当性）」を明記する。

3. **変更内容（What）を具体的に整理する:**
   - 変更した対象ファイルやコンポーネントごとに、具体的に何を追加・変更・削除したかを簡潔に記載する。

4. **客観的な検証結果（Verification）を添える:**
   - 「問題ないと思います」といった主観的感想ではなく、実行したテスト結果、リント、ビルド、ブラウザ動作確認の客観的事実を示す。

5. **絵文字の禁止:**
   - プロジェクト共通規約に則り、絵文字は一切使用しない。

---

## 2. 標準報告フォーマット

承認を求める際、または実行前の判断材料を提供する際は、必ず以下のフォーマットを使用する。

```markdown
コミットおよびデプロイの承認をお願いいたします。判断材料として変更内容と設計意図を以下に報告します。

### 1. 変更の意図・設計方針（Why）
- [背景・課題]: なぜこの修正・機能追加が必要だったか
- [設計方針]: なぜこのアプローチ・構造を選んだか（他案と比較した利点、初学者への配慮、副作用防止など）

### 2. 主な変更内容（What）
- [対象ファイルまたは機能]: 具体的な変更・追加・修正点
- [対象ファイルまたは機能]: ...

### 3. 検証・品質確認結果
- テスト: `npm test`（XX件パス、エラー0件）
- 静的解析・ビルド: `npm run lint` / `npm run build`（エラーなし・ビルド成功）
- 動作確認: 実画面での表示、レスポンシブ表示、コンソールエラーなし等

### 4. コミット予定内容
- メッセージ: `<type>(<scope>): <description>`
```

## 3. 良い報告例 vs 悪い報告例

### 悪い報告例（判断材料が不足・Whyがない・長文）
> 修正が終わりました！
> sketch.js と index.html と articles.ts を直しました。Identity 行列の関数も追加してあります。テストも通ったのでコミットしてデプロイしてもいいですか？

- **問題点:**
  - なぜその修正方針にしたのか（Why）が一切書かれていない。
  - 何をどのように直したのか（What）が具体的にわからない。
  - テストの具体的な結果やビルド確認の有無が不明。

### 良い報告例（簡潔な箇条書き・WhyとWhatが明確・検証結果あり）
> コミットおよびデプロイの承認をお願いいたします。判断材料として変更内容と設計意図を以下に報告します。
>
> ### 1. 変更の意図・設計方針（Why）
> - [視覚化の乖離解消]: 記事本文のテーマ「対角化による累乗計算の高速化」とアニメーション内容が一致していなかったため、直接計算 \(O(n)\) と対角化後 \(O(1)\) の計算量比較グラフおよび実測ベンチマークへ刷新。
> - [認知負荷の低減]: 行列サイズ変更時に初学者が直感的に理解できるよう、恒等写像を表す単位行列生成関数 `Matrix.createIdentity` を導入し、記事末尾にコード解説を新設。
>
> ### 2. 主な変更内容（What）
> - `src/sketch.js`: 理論計算回数の比較折れ線グラフと `performance.now()` による実測実行時間グラフの2段描画処理を実装。
> - `src/core/Matrix.js`: 任意次数の単位行列を生成する `Matrix.createIdentity(size)` 静的メソッドを追加。
> - `public/articles/matrix-diagonalization/index.html`: 実装タブ下部に新規追加コードの完全なブロック表示とステップ解説を追加。
>
> ### 3. 検証・品質確認結果
> - テスト: `npm test`（全23ファイル・113件すべてパス）
> - 静的解析・ビルド: `npm run lint`（警告・エラー0件）、`npm run build`（正常完了）
> - 動作確認: ブラウザ上で累乗計算・ベンチマーク測定が正常動作し、枠はみ出しがないことを確認。
>
> ### 4. コミット予定内容
> - メッセージ: `feat(article): refresh diagonalization visualization with benchmark and add Matrix.createIdentity explanation`

---

## 4. 承認依頼前のセルフチェック

報告を送信する前に、以下を自認・確認すること：
- [ ] 変更の「なぜ（Why）」が課題と設計理由の両面から説明されているか？
- [ ] 変更内容が「簡潔な箇条書き」で整理されているか？
- [ ] テスト結果やビルド状況など客観的な検証結果が含まれているか？
- [ ] 絵文字が含まれていないか？
- [ ] 日本語で記述されているか（コミットメッセージ件名を除く）？
